## How to write expectations (this is what makes the corpus independent)
- Expectations come from **security requirements and the contract**, never from what the system happens to do. Run your tests to debug them, but a check that fails against the system is a **candidate finding**: record it with evidence (request, response, expected vs actual). **You may not weaken, delete or "fix" a check to make it pass.** If you believe a check is itself wrong (it contradicts the written contract), keep it and list it as *disputed* with your reason; the coordinator adjudicates.
- Every security property needs a **positive control** (the legitimate action works) and a **negative control** (the attack is refused), so a passing test proves something.
- No sleeps as synchronisation: wait on explicit readiness conditions. Tests must be deterministic and tolerate a loaded machine (other authors run at the same time).

## Test file format
Each file runs standalone with `node <file>`; it prints a human-readable line for each failed check and ends with ONE JSON line `{"suite":"<name>","area":"<A-D>","checks":N,"failed":M,"failures":["<check id and text>", …]}`. Exit code 0 only if `failed` is 0 (exit 1 if any check failed); exit 2 for infrastructure problems (print `BLOCKED: <reason>`; never turn something that could not run into a pass). Each file must finish in under 10 minutes, start its own server process(es) on free ports with a private temp data location, and clean up everything (processes, containers, temp dirs) in a `finally`. Name checks `"<ID> description"`. ## Generic requirements checklist (cover every item in your area, deeply)
Password authentication; account enumeration (status code, body, timing); login throttling (the correct password must not bypass it; forwarding-header spoofing; concurrent bursts; multiple server instances); API-key and edge-token restrictions on every human-account, session, MFA, step-up, reset and settings route; session issuance; session revocation (account-wide and individual); ordinary logout (a copied cookie must be refused afterwards; other sessions of the same account must survive); password change and reset effects; account deactivation and restoration; deleted-and-recreated accounts; MFA challenges (no authority before completion); TOTP window and replay; WebAuthn (origin, relying party, signature, user verification, counter, challenge reuse); recovery codes (single use, other account, abuse, lock); factor management (enrolment, replacement, removal, last-factor guard, regeneration); step-up (purpose isolation, expiry, session binding, permission loss, forged grants, recovery codes not accepted); administrator recovery (reset; break-glass is off by default, applies once per identifier, preserves the password, has no HTTP route); enforcement policy and grace periods; legacy tokens; database failures (fail closed, honest errors, no internal detail); concurrency; cross-account attempts; forged tokens; expired challenges; permission removal; untrusted forwarding headers; multi-instance and mixed-version behaviour; authentication downgrade attempts; secrets and identifiers never present in responses, logs, audit records or storage.
Known contract limitations you must treat as limitations and **report as Info, not as failures**, if you observe them: a token issued before per-session revocation existed cannot be revoked individually; an older server instance does not know newer revocation records (mixed-version). Everything else is a requirement.
