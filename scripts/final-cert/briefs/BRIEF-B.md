## How to write expectations (this is what makes the corpus independent)
- Expectations come from **security requirements and the contract**, never from what the system happens to do. Run your tests to debug them, but a check that fails against the system is a **candidate finding**: record it with evidence (request, response, expected vs actual). **You may not weaken, delete or "fix" a check to make it pass.** If you believe a check is itself wrong (it contradicts the written contract), keep it and list it as *disputed* with your reason; the coordinator adjudicates.
- Every security property needs a **positive control** (the legitimate action works) and a **negative control** (the attack is refused), so a passing test proves something.
- No sleeps as synchronisation: wait on explicit readiness conditions. Tests must be deterministic and tolerate a loaded machine (other authors run at the same time).

## Test file format
Each file runs standalone with `node <file>`; it prints a human-readable line for each failed check and ends with ONE JSON line `{"suite":"<name>","area":"<A-D>","checks":N,"failed":M,"failures":["<check id and text>", …]}`. Exit code 0 only if `failed` is 0 (exit 1 if any check failed); exit 2 for infrastructure problems (print `BLOCKED: <reason>`; never turn something that could not run into a pass). Each file must finish in under 10 minutes, start its own server process(es) on free ports with a private temp data location, and clean up everything (processes, containers, temp dirs) in a `finally`. Name checks `"<ID> description"`. Locate the SUT with `const SUT = process.env.SUT_DIR || require("path").resolve(__dirname, "../../..");` (the corpus will later be run from `scripts/final-cert/<AREA>/` inside a repository root, three directories up).
