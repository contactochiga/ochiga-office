## 3. Architecture of WhatsApp send paths (audited)
Only Office holds Meta credentials. Office calls Meta from exactly three places, all now governed: (1) `processWhatsAppMessageEvent` — Office's direct reply to an inbound message (autonomous; OFF check before drafting and again immediately before sending, plus a fresh takeover read); (2) the Backend bridge `POST /api/lead-agents/admin/communications/whatsapp/send` — text and template, used by Backend `CommunicationRuntime`'s `WhatsAppAdapter`; (3) new `POST /api/lead-agents/admin/leads/:id/whatsapp/reply` — manual staff reply. Backend has no Meta credentials and no other WhatsApp sender (`grep` for the Graph API / token variables finds only comments). Backend callers of `communicationRuntime.dispatch`: the Oma confirm path (a typed human confirmation), `goalEvaluator` (twice) and `communicationActionBatchExecutionService` (automation) — the latter three are `source: "automation"`, pre-authorized, and are autonomous. `schedule.mode` is stored but nothing dispatches scheduled conversation sends later.

## 4. Global OFF enforcement evidence
Setting `whatsapp_autonomous_responses_enabled` in `office_runtime_settings`: durable (Supabase table + file store), default false (missing row = OFF), read at call time with no cache or process variable, strict reads (error, missing table, non-boolean, string `"true"` ⇒ unknown ⇒ OFF). `scripts/test-whatsapp-autonomy-control.js` proves, on a real HTTP server: default OFF and CRM persistence; Office reply blocked; bridge blocked for missing `lead_id`, unresolved identity, unlabelled sends, template sends, Backend automation/goal labels; a send prepared while ON and dispatched after OFF is blocked; OFF during reply generation blocks the pre-send check; eight concurrent inbound messages cannot bypass OFF; unreadable setting fails closed on webhook, bridge and status; persistence across restarts; switching ON sends nothing and replays nothing. Switching OFF does not touch Meta configuration or webhook handling (the webhook route and signature check are unchanged). A real compiled Backend adapter posting to the real Office bridge (`scripts/test-whatsapp-autonomy-cross-repo.js`) behaved the same: goal OFF → blocked, staff-confirmed → sent, no confirmation evidence → blocked, goal ON → sent.

## 5. Staff-confirmed origin: security assessment and correction
**Finding (bypass, corrected):** the first implementation let any bridge request carry `send_origin: "staff_confirmed"` as an untrusted string; anything able to call the bridge with the shared key (including a defective or compromised Backend path, or an injected request) could skip the OFF switch. Backend also derived the label from `record.source === "conversation"` alone.
**Correction (narrow):**
- Backend declares `staff_confirmed` only when the record is conversation-sourced, `requires_confirmation` is true, `authorize()` recorded a `confirmation_id`, and an authenticated staff `actor_id` is attached; it then attaches an HMAC-SHA256 attestation over `communication_id | confirmed_by | confirmation_id | to | sha256(content) | confirmed_at` keyed by the existing shared bridge key (no new secret). Goals, automations, tasks, workflows and unconfirmed conversation records never get one.
- Office treats a send as autonomous unless the attestation verifies (key, fields present, ≤ 10 min old, ≤ 60 s skew, content/recipient/communication id match, constant-time compare). Bare labels, empty/partial attestations, wrong or non-hex signatures, tampered body/recipient/template swap, stale or future timestamps and a wrong key are all refused while OFF; rejections are audited (`communication.whatsapp.origin_rejected`). Verified staff sends are audited with `confirmed_by` and `confirmation_id`. A shared test vector is asserted in both repos.
- Answers to the audit questions: origin is set server-side from the persisted record, not from a request parameter (1,2); the actor id comes from the authenticated Oma session (`context.actor`) (3); the confirmation is a deterministic match on the staff member's own typed "yes" tied to the pending pointer for the same thread and actor — an AI response cannot produce it (5,7); identity and confirmation evidence are forwarded and audited in Office (6); templates use the same attestation (8); the manual reply route now requires `crm.manage` **and** `human_status ∈ {human_active, human_review}` (an AI pause alone is not a takeover) (9); forged metadata is rejected (10).
**Residual trust assumptions (not credible bypasses):** the shared bridge secret is the root of trust, so a party holding it can sign an attestation; use a separate signing secret later if you want that separation. Staff permission to send WhatsApp is enforced by Backend's conversation capability layer, not re-checked by Office. `CommunicationRuntime.dispatch` does not itself verify `status === "confirmed"`; today's four callers are accounted for above, and an unconfirmed record would not carry a confirmation id, so it would be labelled autonomous and blocked while OFF.

## 6. Human takeover verification
Inbound messages no longer write `human_status` (new rows take the stored default); tests prove takeover and owner survive a new inbound message (a mutation putting the reset back makes the test fail). Per-lead `ai_paused` and active takeover override global ON on both Office replies and the bridge. The pre-send check re-reads takeover so a takeover started during drafting wins.

## 7. Duplicate protection
In-process claim set plus store check, plus an atomic claim by inserting the inbound event: Supabase unique index `inbound_events_message_once` (409 ⇒ duplicate) and the file store's equivalent. Six concurrent deliveries of one message id produced one reply and one stored event. Blocked replies are not recorded as delivered: the "intelligence turn" timeline entry is written only after a send, suppressed replies leave a `whatsapp_autonomous_reply_suppressed` note and a CRM activity with `ai_replied:false`; nothing is queued. Caveat: when a takeover/OFF arrives after Oyi Core has already produced a reply, Core's own thread still contains that unsent answer (a narrow race; Office does not record it as sent).

## 13. Rollback
Fast path: switch OFF in Settings (or `PUT … {enabled:false}`) — immediate, no deploy. Code rollback of Office reverts to the old always-autonomous behaviour, so do **not** roll Office back without first deciding how replies stay off (if unavoidable, an emergency measure such as unsetting the WhatsApp send credentials is an environment change that needs your approval). Backend rollback is safe: Office then treats every bridge send as autonomous (blocked while OFF). The migration may stay; to remove it after both code rollbacks: `drop index inbound_events_message_once; drop table office_runtime_settings;`.
