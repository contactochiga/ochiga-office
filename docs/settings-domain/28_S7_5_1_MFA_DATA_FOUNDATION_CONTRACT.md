# S7.5.1 — MFA data foundation: frozen implementation contract

Branch `feature/settings-s1-s2`, starting HEAD `2f07ff2` (local = remote, clean worktree verified). Implements the data layer of `25_S7_5_MFA_ARCHITECTURE_AND_RECOVERY_DESIGN.md` (§5, §6, §20) on top of the completed S7.5.0 hardening. **This slice adds storage, atomic database functions, store contracts and key-configuration readiness only.** Out of scope and absent after this slice: MFA enrollment, login challenges, passkey registration, recovery-code generation or display, enforcement stages, UI, step-up MFA leg, MFA routes of any kind, S7.5.2, merging, deploying, and any production migration or key.

## 1. Default state
`LEAD_AGENTS_MFA` defaults to **off**. With MFA off nothing in the running system changes: no route, login path, session claim, step-up rule or UI reads or writes an MFA table. `LEAD_AGENTS_MFA=on` in this slice only turns on **key validation and readiness reporting** (§6) — it does not create any behaviour for users. A source-scan test proves no route or handler references any MFA store method.

## 2. Schema (additive migration `db/20261022_admin_mfa_foundation.sql`)
- `admin_users` gains `mfa_required_after timestamptz`, `mfa_failed_attempts integer not null default 0 (>= 0)`, `mfa_locked_until timestamptz`, `mfa_reset_at timestamptz`, `mfa_reset_by text`. Existing rows keep all values; new columns default to "no MFA, no failures".
- `admin_mfa_credentials`: id, `admin_user_id` (FK, `on delete cascade`), `type` (`totp`|`webauthn`), `label`, `status` (`pending`|`active`|`revoked`), TOTP columns (`secret_ciphertext`, `secret_nonce`, `secret_key_id`, `totp_last_step bigint not null default 0`), WebAuthn columns (`webauthn_credential_id bytea unique`, `webauthn_public_key`, `webauthn_sign_count`, `webauthn_transports`, `webauthn_aaguid`, `webauthn_backup_eligible`), lifecycle timestamps and `revoked_by/reason`; a check constraint requires the secret material appropriate to the type; a partial unique index allows **one pending-or-active TOTP per account**.
- `admin_mfa_recovery_codes`: id, user (FK cascade), `batch_id`, `code_hmac text unique`, `created_at`, `used_at`. Only keyed hashes are stored.
- `admin_mfa_challenges`: id, user (FK cascade), `purpose` (`webauthn_register`|`webauthn_authenticate`), `challenge bytea`, `created_at`, `expires_at`, `consumed_at`.
- Credential and challenge secrets are **ciphertext or public material only** (design §5); the encryption itself is S7.5.2 — this slice stores and moves opaque values and never interprets them.
- Re-applying the migration is a no-op (`if not exists` / guarded constraints and `create or replace`).

## 3. Access control
All three tables: `row level security` enabled with **no policies**; every privilege revoked from `public`, `anon`, `authenticated`; only `service_role` receives `select, insert, update` (and `delete` where a function needs it: recovery codes and challenges). Every function: `revoke all from public/anon/authenticated`, `execute` only for `service_role` (the S3/S7.4 guarded-`do` pattern so the file also applies on plain Postgres fixtures). New `admin_users` columns inherit the table's existing denial for the Data API roles; the migration asserts and the tests verify that no new privilege reaches them.

## 4. Atomic functions (service role only)
| Function | Contract |
|---|---|
| `office_mfa_schema_version()` | pure capability probe, returns `1` |
| `office_mfa_consume_totp_step(credential_id, step)` | single compare-and-set: succeeds (true) only for an **active TOTP** whose stored `totp_last_step` is strictly lower; records `last_used_at`; replay, older step, revoked/pending/unknown credential ⇒ false |
| `office_mfa_consume_recovery_code(user_id, code_hmac)` | claims an unused code of **that user** exactly once (true/false) |
| `office_mfa_replace_recovery_codes(user_id, batch_id, hmacs[])` | in one statement deletes the user's unused codes and inserts the new batch, returns the count; used codes stay as history. A storage primitive: nothing generates or shows codes in this slice |
| `office_mfa_create_challenge(user_id, purpose, challenge_b64, ttl_seconds)` | inserts, returns id and expiry |
| `office_mfa_consume_challenge(challenge_id, user_id, purpose)` | single use: unexpired, unconsumed, same user **and** purpose ⇒ returns the challenge (base64) once, otherwise null |
| `office_mfa_record_failure(user_id)` | atomic increment of the account's failure counter and lock computation: ≥ 5 ⇒ lock 1 min, ≥ 10 ⇒ 15 min, ≥ 20 ⇒ 60 min (never shortens an existing lock); returns attempts and `locked_until` |
| `office_mfa_clear_failures(user_id)` | resets counter and lock |
| `office_mfa_reset(user_id, actor)` | one statement: revoke pending/active credentials (`revoked_reason = 'reset'`), delete unused recovery codes, set `mfa_reset_at/by`, clear failures **and bump `session_generation`**; returns generation and counts. Unreachable: no caller in this slice |
| `office_mfa_prune_challenges(older_than)` | deletes expired/consumed challenges older than the interval |

## 5. Store contracts (file store and Supabase store, identical semantics)
`supportsMfa`, `createMfaCredential`, `activateMfaCredential` (pending→active, compare-and-set), `revokeMfaCredential`, `listMfaCredentials` (**sanitised**: never ciphertext, nonce, key id, public key or counters' secrets), `getMfaCredentialSecret` (the only reader of secret columns), `consumeTotpStep`, `replaceMfaRecoveryCodes`, `consumeMfaRecoveryCode`, `countMfaRecoveryCodes`, `createMfaChallenge`, `consumeMfaChallenge`, `recordMfaFailure`, `clearMfaFailures`, `getMfaLockState`, `resetMfa`, `pruneMfaChallenges`. Rules: every operation is scoped by user id (cross-user use fails); **fail closed** — a store or transport failure throws a sanitised error (`code`, HTTP status only; never the request body, ciphertext, HMAC, challenge or key) and never reports success; capability absent (migration not applied) ⇒ `mfa_unavailable`; the file store applies the same state machine in its single writer and rolls an operation back if the disk write fails.

## 6. Key configuration and readiness
Configuration only (no key is generated, stored in the repository, written to the database or exposed): `LEAD_AGENTS_MFA` (`off` default | `on`), `LEAD_AGENTS_MFA_KEY` (32 random bytes, Base64), `LEAD_AGENTS_MFA_KEY_ID` (1–32 of `[A-Za-z0-9._-]`), optional `LEAD_AGENTS_MFA_KEYS_PREVIOUS` (`id:base64,…` for rotation).
`validateMfaConfig` is evaluated live and reports **problem codes only**: `mfa_key_missing`, `mfa_key_invalid_encoding`, `mfa_key_wrong_length`, `mfa_key_weak` (low-entropy, e.g. repeated bytes), `mfa_key_id_missing`, `mfa_key_id_invalid`, `mfa_key_reused_secret` (equal to the session secret, an API key, an edge token, a bridge secret or another shared secret, as bytes or text), `mfa_previous_key_invalid`, `mfa_previous_key_id_duplicate`. The key must be independent of the session secret (rotating the session secret is the S7.4 break-glass and must never affect MFA).
`/healthz` gains `mfa: { mode, key: not_required|configured|missing|invalid, schema: available|unavailable|unknown|not_checked, problems? }`; with MFA **on** and an invalid key it answers **503** (`ok:false`) exactly like an invalid session secret; with MFA off an absent key is `not_required` and never affects readiness. No key, key length, key id value or fingerprint is ever reported or logged. The deployment validator rejects `value:` entries for the key variables and `LEAD_AGENTS_MFA` set to `on` in `render.yaml`; `.env.example` documents the names (commented, no values).

## 7. Rollback
`db/rollback/20261022_admin_mfa_foundation.down.sql` is **non-destructive**: it drops the functions only; tables, columns and rows are kept (dropping credentials silently downgrades protected accounts). Optional destructive statements are commented and for non-production only. Feature rollback is configuration (`LEAD_AGENTS_MFA=off`, the default).

## 8. Required tests (disposable Postgres 16 and Supabase Postgres 17 + PostgREST, real `SupabaseLeadAgentsStore`)
Migration idempotence and non-disturbance of existing accounts; additive columns; constraints (type/material, one TOTP, status); **credential isolation** (privilege matrix for `public`/`anon`/`authenticated`/`service_role` on tables and functions, REST and SQL refusals, no policies, RLS on, cross-user operations fail, sanitised listings); **concurrency** (same TOTP step 20-way ⇒ one winner; increasing steps never accepted twice; recovery code, challenge and activation single winners; 60-way failure counting exact; replace-batch races leave exactly one batch); **database failures** (transport down, malformed responses, capability absent ⇒ throw, never success; file-store persist failure rolls back); **rollback** (functions gone, data intact, re-apply works); **secret redaction** (errors, healthz, logs and audit carry no ciphertext, HMAC, challenge or key); key validation matrix; default-off proof (no route references MFA, `/healthz` mode off, login unchanged). Regressions: S7.0–S7.5.0 suites, the full Office regression, repository gates.
