Baseline R9 `ef0af76`. Runtime/schema commit `5db4bb8` (+ this document). Clean-checkout evidence: `s7-official-results/r10full`; adjudication runs: `s7-official-results/r10`. Nothing was merged, deployed, applied to production, or MFA-enforced. No production system was contacted.

## A. Trusted-proxy chain — status: **UNKNOWN (no authorized read-only evidence available); `LEAD_AGENTS_TRUSTED_PROXY_HOPS` stays 0**
Evidence available in the repository only: `render.yaml` runs the app as a Render web service and sets no proxy variable; `vercel.json` rewrites `/api/lead-agents/*`, `/webhooks/*`, `/healthz` etc. from the public domain to `https://ochiga-lead-agents.onrender.com`. So there are at least two request paths into the same process:
1. public domain → Vercel → (rewrite) → Render edge → app, and
2. a direct request to the `onrender.com` origin → Render edge → app.
The vendors' actual header behaviour (what Vercel writes into `X-Forwarded-For` on a rewrite, how many entries Render's edge appends) is not recorded in the repo and was **not** inferred from documentation. No Render or Vercel project access was available in this session, and sending probe traffic to production was not authorized.
Why the number cannot be guessed: the application takes the N-th entry from the right. Modelled in `scripts/test-proxy-boundary-r10.js` (P2): with N=2 (client + front-end egress) a request sent straight to the origin carries a client-forged entry in the trusted slot and is **accepted as that identity** — so any N larger than the shortest path into the origin is spoofable. N=1 (the entry Render's own edge appends) is spoof-proof on both paths but identifies the front end's egress address for proxied traffic, not the user. N=0 ignores the header everywhere and is the safe default (per-account budgets remain; per-address budgets become per-egress-address).
**How the owner establishes the chain (new, read-only):** `GET /api/lead-agents/admin/diagnostics/client-address` (signed-in administrator with `settings.manage`; no API key, edge token or other role) returns what the application derived for that very request: configured hops, resolved address, peer address, the last 8 `X-Forwarded-For` entries and the true entry count. Procedure: (a) call it from the browser through the public domain; (b) call it directly against the `onrender.com` origin with a forged `X-Forwarded-For: 192.0.2.1`; (c) choose the smallest N for which the N-th entry from the right is the expected address on BOTH paths (or close the direct path); (d) set `LEAD_AGENTS_TRUSTED_PROXY_HOPS` in the Render dashboard and re-run (a)/(b); `/healthz → rate_limit.trusted_proxy_hops` confirms the value. Not applied by this change.
**Decision recorded:** keep 0 until (a)-(d) are done by the owner. Consequence of 0 in production today: sign-in/step-up/reset budgets are per account (the per-address dimension collapses to the proxy's address); an attacker still cannot create fresh budgets by forging headers; a single account can be throttled by anyone who knows its e-mail (bounded, 15 min, existing R1 behaviour).

Not a DoS defect before (work was bounded by the 1 MB body limit). |
