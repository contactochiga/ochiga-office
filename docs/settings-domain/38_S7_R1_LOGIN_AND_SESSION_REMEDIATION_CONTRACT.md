## 1. Root causes (read from `server.js` login route, `auth.js`, `rate-limit.js`)
**F-1 — limiter bypass.** (a) The route verifies the password **before** consulting the limiter and, when the limiter has tripped, does `if (credentialsValid) { resetKey(...) } else { 429 }`: a correct password erases the limit and proceeds, so the limiter changes only the status of *wrong* guesses and a guesser can tell success from failure by `200` versus `429` with no throttling. (b) The limiter key is `email:ip` where the address is the **first** `X-Forwarded-For` element, which a client can set freely: rotating that header starts a new bucket every attempt, so even a strict limiter would be bypassed. (c) The limiter lives in process memory, so each running instance enforces its own count.
**F-2 — inactive-account oracle.** The route tests `adminUser.status !== "active"` **before** it tests the password and answers `403 account_inactive`, so anyone can learn that an address belongs to a deactivated account without knowing its password. Unknown and wrong-password cases answer `401`.
**F-3 — timing oracle.** `credentialsValid` is `Boolean(adminUser && verifyPassword(...))`: when no account exists the expensive scrypt verification never runs (≈0.6 ms) while an existing account costs ≈35 ms (median ratio ≈60× in the certification run).
**F-4 — lax token structure.** `readAdminSession` destructures `String(rawToken).split(".")` into two names and ignores any further segments, so `payload.signature.anything` verifies. (Step-up, MFA challenge and public-session tokens already reject a third segment.)

## 2. Existing behaviour → corrected behaviour
| | Today | After R1 |
|---|---|---|
| Order | lookup, **password hash**, then limiter | limiter **first** (no lookup, no hashing for a limited caller), then lookup, then password |
| After the limit | wrong → `429`, **right → `200`** | **every** attempt → the same `429` body, whatever the password; the right password does **not** reset the limit |
| Key | `email:first-X-Forwarded-For` only | unchanged per-address key **plus** a per-account failure ceiling keyed by the normalised e-mail alone (5 × the per-address limit, same window), which an address-rotating attacker cannot escape |
| Success | resets the per-address counter | unchanged (per-address counter only); the per-account failure count is **not** cleared by a success |
| Inactive account | `403 account_inactive` before the password check | verified like any account; **wrong password, unknown account and inactive account (any password) all answer the identical `401` body**. Deactivation is still enforced (no session is ever issued for a non-active account). A denied inactive sign-in is audited by category (`session_login_denied_inactive`, user id, no password data) |
| Unknown account | no hash computed | a fixed **dummy** scrypt hash with the same parameters is verified, so the same work is done |
| Token | extra segments ignored | exactly two non-empty segments or the token is refused. Valid existing tokens (`base64url(payload).hex(hmac)`) are unaffected |

## 3. Design notes and honest limits
- Per-process state: with N instances a guesser gets at most N× the limit per window from the per-address count and N× the per-account ceiling. R1 does not add shared storage (that needs a migration and is a separate slice); the multiplication is tested as a documented bound.
- The per-account ceiling can be used to slow a victim's sign-in for the remainder of the window (the standard trade-off). Mitigation kept: the ceiling is 5× the per-address limit, the window is the existing 15 minutes, and MFA verification keeps its own persisted lock.
- `X-Forwarded-For` trust is **not** changed (behind the deployment proxy that would collapse all users into one address); the account ceiling is what bounds a spoofing attacker. Recorded as a remaining observation.
- Timing: the dummy verification removes the dominant difference (the hash). Remaining differences (store lookup, JSON, audit writes on the real path) are not eliminated; R1 **does not claim constant time**. Acceptance: the median unknown-account time is within 25 % of the existing-account wrong-password median over 60 interleaved samples each, measured before and after in the same conditions; distributions (min, median, p90, max) are reported.
- `scryptSync` blocks the event loop for ~35 ms per attempt (a throughput limit, not an oracle); unchanged and noted.

## 5. As built
- `rate-limit.js`: `hit`, `isLimited`, `resetAtOf` (failure-only counter helpers; `checkKey` unchanged).
- `auth.js`: `readAdminSession` requires exactly two non-empty segments; `verifyPasswordOrDummy` (module-level dummy scrypt hash) exported.
- `server.js` login route: limiter first (per-address `checkKey`, then the per-account failure ceiling `isLimited`), uniform `429`; password verified for every request; a single `401` answer for wrong password, unknown account and inactive account; audit `session_login_denied_inactive` (category only) when a correct password meets an inactive account. The per-account limiter is created beside the existing one (5 × its `maxRequests`, same window).
