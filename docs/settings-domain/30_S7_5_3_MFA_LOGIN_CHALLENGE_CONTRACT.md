# S7.5.3 — MFA login challenge and verification: frozen contract

Branch `feature/settings-s1-s2`, starting HEAD `c681606` (local = remote, clean worktree verified). Builds on S7.5.1 (schema, atomic store operations), S7.5.2 (crypto library) and the S7.0–S7.5.0 authentication system, which it **extends rather than replaces**: the same password verification, limiter, `issueSession`, S7.3 duration, S7.4 generation and S7.5.0 password binding. Out of scope: enrollment, passkeys/WebAuthn login, recovery-code issuance flows, enforcement stages ("required for accounts without a factor"), e-mail notifications, UI, S7.5.4, merging, deploying, production migration.

## 1. When MFA applies
`LEAD_AGENTS_MFA` defaults to **off**: login is exactly as before for every account (a declared downgrade; `/healthz` reports `mfa.enrolled_accounts` so enrolled accounts being ignored is visible). With MFA **on**, an account is *MFA-required* iff it has an **active** credential (S7.5.1 `status = 'active'`). Accounts without one keep today's login unchanged — enforcement of enrolment is not part of this slice. An enrolled factor is never ignored once MFA is on.

## 2. Flow
1. `POST /admin/session/login` — password verification, limiter and error responses **unchanged**. After the password is proven (never before, so unknown or wrongly-authenticated callers learn nothing) and the account is active, the server checks enrolment. If MFA-required it answers `200 { ok:false, mfa_required:true, challenge_token, expires_at, methods:["totp","recovery_code"] }`: **no cookie, no `admin` object, no authority** (the challenge is not a session; presenting it as a cookie, Bearer token or step-up grant fails everywhere). The login limiter is **not reset** by a password success that still needs a second factor; it resets on full success.
2. `POST /admin/session/mfa/verify` — public path (no session exists yet). Body `{ challenge_token, method:"totp"|"recovery_code", code }`.
3. On success the server issues the **existing** governed session through `issueSession`, adds `mf:1` and `mft` (ms), updates `last_login_at`, resets limiter and failure counters, audits, and answers like a normal login (`{ ok:true, admin, mfa:{ method, recovery_codes_remaining? } }` plus the cookie).

## 3. Challenge issuance
S7.5.2 `issueChallengeToken` (purpose `login`, 5 min, ceiling 10): signed with the HKDF challenge subkey, bound to account id, password fingerprint and session generation. Issued only for a correct password on an MFA-required account. Audit `mfa_challenge_issued` (account, request id; never the token).

## 4. Verification (`mfa/verify`)
Order of checks: auth configuration valid (503) → MFA on (503 `mfa_unavailable`) → `challenge_token` present and its **unverified** subject read to load the live account (S7.5.2 `challengeSubject`) → existing login limiter keyed `mfa|ip|email` (429) → persisted lock (`getMfaLockState`; locked ⇒ 429 `mfa_locked` with `retry_after_seconds`, **no attempt is counted while locked**, so a hammering attacker cannot extend a victim's lock) → `verifyChallengeToken` against the **live** account → method dispatch → outcome.
Responses (no oracle between causes): `401 mfa_challenge_expired` for expired / password changed / generation revoked (re-login needed); `401 mfa_failed` for everything else (forged, wrong purpose, unknown/mismatched account, bad or replayed code, malformed input, unknown method); `429` for limiter/lock; `503 mfa_unavailable` (key configuration invalid, key id missing, decrypt failure, schema absent) and `503 mfa_verification_unavailable` (store errors) — **always fail closed, never password-only**. `webauthn` is rejected (`400 unsupported_method`).
- **TOTP:** the account's active TOTP credential is verified with S7.5.2 `verifyAndConsumeTotp` (the S7.5.1 single-statement compare-and-set). Wrong ⇒ `mfa_failed`; same or older step ⇒ replay ⇒ `mfa_failed` (audit reason `replay`).
- **Recovery code:** S7.5.2 `verifyAndConsumeRecoveryCode` (single-use atomic). Success additionally **bumps the session generation** through the existing revocation path (other sessions end, per decision D-3) and returns the remaining count.
- **Failures:** every genuine failure calls `recordMfaFailure` (S7.5.1: 5 → 1 min, 10 → 15 min, 20 → 60 min locks) and the limiter; success calls `clearMfaFailures`. Server-side faults (decrypt, key, store) are **not** counted against the user.
- The challenge itself is stateless and not single-use; it grants nothing without a fresh valid factor, replay of factors is refused by the store, and any password change, generation bump or expiry kills it.

## 5. Session issuance
`issueSession` is reused unchanged in behaviour: S7.3 duration (token `exp` = cookie `Max-Age`), S7.4 generation re-read, S7.5.0 `pf` from the hash the credentials were verified against, cookie flags. New claims `mf` (1) and `mft`. `readAdminSession`/`authenticateSessionCookie` expose them as `sessionMfa`/`sessionMfaAt`. Re-issues that keep a browser signed in (self password change, `revoke-all keep_current`) **carry the MFA claims over** from the session being replaced. `/session/me` reports `mfa_verified`.
**Policy check in the single verifier (`enrichAuthContext`, so `/session/me` and every protected route get it):** with MFA on, an account that has an active credential must present a session with `mf = 1`, otherwise `401 mfa_required` (this retires pre-enrolment and legacy cookies without a mass revocation). Store errors there ⇒ 503, never accept.

## 6. Legacy paths
With MFA on: the transitional API-key-as-password login is refused (and `validateMfaConfig` reports `mfa_enabled_with_api_key_login`, making `/healthz` 503); invite accept and reset confirm are unchanged (they issue no MFA-bypassing session for an enrolled account: invite accept targets accounts in `invited` state, which cannot have factors yet; reset confirm issues no session). API keys remain unable to reach any MFA route or human-account mutation (S7.5.0).

## 7. Recovery-code key identification (schema change, additive)
Recovery hashes depend on the key that existed at creation and S7.5.1 stored no key id, forcing verification to try every key and making safe key retirement a manual rule. **Additive migration `db/20261023_admin_mfa_recovery_code_key_id.sql`:** `admin_mfa_recovery_codes.key_id text` (null for existing rows) and `office_mfa_replace_recovery_codes` gains an optional `p_key_id` (the 3-argument overload is replaced, grants re-applied; callers that omit it keep working). Store: `replaceMfaRecoveryCodes(…, {keyId})`, `listMfaRecoveryKeyIds(userId)`, `countUnusedRecoveryCodesNotUsingKey(keyId)`. Crypto: `newRecoveryBatch` returns the key id; `verifyAndConsumeRecoveryCode` computes candidates only for the key ids actually present on the account's unused codes (legacy `null` rows ⇒ every ring key); `recoveryCodesBlockingRetirement({store, keyId})` reports how many unused codes still depend on a key, so a previous key can be retired only when it is 0. Before the migration the store reports `mfa_schema_outdated` and verification falls back to trying every ring key (no outage). Rollback restores the 3-argument function and keeps the column and data. Not applied to production.

## 8. Rate limiting and lockout
Reuses the existing `adminLoginRateLimiter` (10 attempts / 15 min per IP + email, namespace `mfa|`) **and** the persisted per-account counter and time-limited locks. A password-correct login that returns a challenge consumes limiter budget until full success. Locks never become permanent. Unknown accounts and non-MFA accounts are indistinguishable from today at every step before the password is proven.

## 9. Readiness and observability
`/healthz` `mfa`: `enrolled_accounts` (count or null), and with MFA **on** the response is 503 when the key configuration is invalid **or the MFA schema is unavailable** (fail closed, consistent with login). Audit actions: `mfa_challenge_issued`, `mfa_verified`, `mfa_failed`, `mfa_locked`, `mfa_recovery_code_used`, `mfa_verification_error`, `sessions_revoked_mfa_recovery_code`: actor/account, request id, method, outcome, failure category, timestamp; never a code, token, secret or hash.

## 10. Compatibility and rollback
MFA off (default): byte-for-byte the previous behaviour for every route; tokens gain nothing. Mixed fleet: an instance without this code ignores `mf` and accepts a password alone for an enrolled account (concern C3 applies; raise MFA only after the single-swap rollout). Rollback: `LEAD_AGENTS_MFA=off` (instant, a declared downgrade), or redeploy; schema is untouched by rollback except the optional 20261023 down file, which keeps data. No MFA stage above "enrolled factors are honoured" exists, so nothing can lock out an account that has no factor.

## 11. Required tests
Correct password + correct TOTP/recovery; correct password + wrong code; password-only bypass attempts (challenge used as cookie, Bearer, step-up; missing/unknown method; another account's code; pre-enrolment `mf=0` cookie; forged or tampered `mf`; API-key fallback); expired, forged, wrong-purpose, wrong-account, password-changed and revoked challenges; 20-way concurrent replay with exactly one session; recovery-code single use and generation bump; session claims (`mf`, `mft`, `sg`, `pf`, S7.3 duration, cookie flags) and re-issue carry-over; account enumeration (identical responses for unknown, wrong-password and garbage-token paths); limiter and persisted lockout progression; database outages at every store call and key/decrypt failures (all fail closed); key rotation (TOTP and recovery codes, retirement readiness); redaction across responses, audit and logs; migration 20261023 idempotence, function replacement, rollback and real-database store behaviour (Postgres 16, Postgres 17 + PostgREST). Regressions: S7.0–S7.5.2, S3 Postgres, WhatsApp, Team permissions, full suite, gates.

## 12. Implementation notes (added after build; the frozen behaviour above is unchanged)
- **Account-store failure at the password step:** found by the real-database outage test. The login route let a raw driver error through (`connect ECONNREFUSED <internal host:port>`). It is now a generic `503 sign_in_unavailable`; no session, challenge or detail is produced.
- **Existing guards updated on purpose:** S7.5.0's write inventory counts the new `last_login_at` write in the verify route (12 `updateAdminUser` sites, challenge-gated); S7.5.1's "unreachable" proof now allows only the login-time store methods and exactly one MFA path (`/session/mfa/verify`); S7.5.2's import proof allows only the two entry points the login challenge needs. Enrollment, issuance, reset and management remain unreachable from `server.js`.
- **Readiness tightened (fail closed):** with MFA on, `/healthz` is 503 when the MFA schema is unavailable as well as when the key configuration is invalid.
- **Retirement counter is store-wide:** `recoveryCodesBlockingRetirement` counts unused codes across all accounts that are not hashed under the current key; a previous key may be dropped only when it reaches 0.
- **Known limitations:** no UI for the second step (the existing sign-in page does not yet render the challenge: a later slice); no enrollment, so accounts become MFA-required only when a factor is created directly in the store; e-mail notifications for recovery-code use are not sent yet; the challenge token is stateless and not single-use (it grants nothing without a fresh factor); a burned recovery code is not restored if the follow-on generation bump fails (the person retries with another code).
