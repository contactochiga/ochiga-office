# S7.5.2 — MFA cryptographic foundation: frozen implementation contract

Branch `feature/settings-s1-s2`, starting HEAD `21f84d2` (local = remote, clean worktree verified). Implements the cryptography of `25_S7_5_MFA_ARCHITECTURE_AND_RECOVERY_DESIGN.md` (§3–§5) on the S7.5.1 schema, atomic functions and store contracts (`28_S7_5_1_MFA_DATA_FOUNDATION_CONTRACT.md`). **Library code only.** Out of scope and absent after this slice: login challenges, enrollment or any MFA route, passkey registration, recovery-code display/issuance flows, enforcement, UI, production secrets or migrations, merging, deploying, S7.5.3. MFA stays off by default: every keyed operation throws `mfa_unavailable` unless `LEAD_AGENTS_MFA=on` **and** the S7.5.1 key configuration validates; `server.js` imports none of this module (source-scan test).

## 1. Module `src/lead-agents/mfa-crypto.js`
Keyless primitives (pure, no configuration): HOTP/TOTP, Base32, `otpauth://` URI, TOTP secret generation, recovery-code generation/normalisation, `hkdfSubkey`. Keyed API from `createMfaCrypto(config)`: TOTP secret encryption/decryption/rotation, recovery-code hashing and consumption, signed challenge tokens, replay-protected verification. Secrets are Node `Buffer`s, zeroised best-effort after use (JavaScript gives no stronger guarantee; stated as a limitation).

## 2. TOTP (RFC 4226 / RFC 6238)
HOTP = dynamic truncation of HMAC; TOTP counter = `floor(unixSeconds / period)`. Defaults per decision D-6: SHA-1, 6 digits, 30 s; SHA-256/512 and 8 digits are implemented so the RFC vectors can be proven, but `createMfaCrypto` enrolls only the defaults. Verification window ±1 step (configurable 0–2 in the function, fixed at 1 by callers). Input rules: a code is exactly `digits` ASCII digits after removing spaces/hyphens; anything else (Unicode digits, wrong length, letters) is `invalid` without computing. Candidate codes for all window steps are always computed and compared with `crypto.timingSafeEqual`, so timing does not reveal which step matched. Secrets: 160 random bits (`crypto.randomBytes(20)`), Base32 without padding for display/`otpauth` (issuer "Ochiga Office").
**Replay protection uses the S7.5.1 operation only:** `verifyAndConsumeTotp` finds the matching step then calls `store.consumeTotpStep(userId, credentialId, step)` (the single-statement compare-and-set). No second replay store, cache or counter exists. Result categories: `ok`, `invalid` (no step matches) and `replay` (the code matched but the step is not newer than the last accepted).

## 3. Key derivation (HKDF-SHA256, purpose separated)
`hkdfSubkey(ikm, purpose)` = HKDF(SHA-256, ikm, salt = `ochiga-office/mfa/v1`, info = `ochiga-office/mfa/v1/<purpose>`, 32 bytes). Purposes (closed allow-list, unknown ⇒ throws): `totp-secret-encryption`, `recovery-code-hmac`, `mfa-challenge-signing`, `mfa-challenge-binding`. Encryption and recovery-code subkeys derive from the **MFA master key** (S7.5.1 `LEAD_AGENTS_MFA_KEY`); challenge subkeys derive from the **session secret** (design §3: rotating the session secret, the S7.4 break-glass, must also kill pending challenges; the MFA master key is never derived from or equal to it, enforced since S7.5.1). A subkey for one purpose never works for another.

## 4. TOTP secret encryption (AES-256-GCM)
Per record: random 96-bit nonce (`crypto.randomBytes(12)`, never reused with a key), 128-bit tag appended to the ciphertext; stored as the S7.5.1 columns `secret_ciphertext` (Base64, ciphertext‖tag), `secret_nonce` (Base64), `secret_key_id`.
**Authenticated metadata (AAD)** = `ochiga-office/mfa/totp/v1|<adminUserId>|<credentialId>|<keyId>` (UTF-8). Consequences: a ciphertext cannot be moved to another credential or account, and the key id cannot be relabelled; any mismatch, tamper, truncation, wrong key or wrong AAD yields the same code-only error `mfa_decrypt_failed` (no oracle between causes). The credential id is therefore chosen by the application before the row exists: the S7.5.1 `createMfaCredential` gains an optional, validated UUID `id` (additive; behaviour without it unchanged).

## 5. Key identification and rotation
Records carry the key id used; decryption selects the key by id from the keyring (current + previous, S7.5.1 `LEAD_AGENTS_MFA_KEYS_PREVIOUS`); unknown id ⇒ `mfa_key_unavailable`. New encryptions always use the current key. `needsRotation(record)` is true when `secret_key_id` differs from the current id. `rotateSecretRecord` decrypts and re-encrypts under the current key with a fresh nonce. Persisting uses a new store compare-and-set, `rotateMfaCredentialSecret(userId, credentialId, {expected: {key_id, ciphertext}, next: {key_id, ciphertext, nonce}})`, one statement guarded by the old key id **and** old ciphertext (a concurrent change, a revocation or a second rotator makes it a no-op `false`; nothing is overwritten). `listMfaCredentialsNotUsingKey(keyId, limit)` returns only ids and account ids (never secrets). `rotateCredentialSecrets({store, limit})` returns **counts only** (`scanned`, `rotated`, `skipped`, `failed`). Key material, key ids and plaintext are never returned, logged or placed in errors; the keyring object hides its keys behind private fields (`JSON.stringify`/`util.inspect` show nothing).
**Recovery-code rotation rule (documented limitation):** recovery-code hashes depend on the key that existed when the batch was created and the schema stores no key id for them, so verification tries the current key and then each previous key. A previous key must therefore stay in `LEAD_AGENTS_MFA_KEYS_PREVIOUS` until every account's recovery codes have been regenerated; retiring it earlier makes those codes unusable (an operational step, not a data loss: affected users re-issue codes).

## 6. Recovery codes
Generated from `crypto.randomBytes`, **10 characters of Crockford Base32 (50 bits)** per code, displayed as `XXXXX-XXXXX`; batches of 10 are checked for uniqueness. Normalisation: case-insensitive, spaces/hyphens ignored, `O→0`, `I/L→1`, anything else invalid (no store call). Hash = `HMAC-SHA256(subkey("recovery-code-hmac"), "ochiga-office/mfa/recovery/v1|" + adminUserId + "|" + normalisedCode)`, Base64url (43 chars, fits the S7.5.1 column constraints); binding the account id makes hashes non-transferable. Consumption: `verifyAndConsumeRecoveryCode` calls the S7.5.1 single-use `consumeMfaRecoveryCode` per candidate key. Plain codes exist only in memory at generation time (no persistence, no logging in this slice).

## 7. Challenge tokens
`base64url(payload).hex(HMAC-SHA256)` with the `mfa-challenge-signing` subkey; payload `{v:1, uid, purpose:"login"|"enroll", pf, sg, iat, exp, jti}`. `pf` is a keyed fingerprint (subkey `mfa-challenge-binding`) of the account's password hash; `sg` the account's session generation. Lifetime default 5 minutes, hard ceiling 10. Verification takes the **live** account and refuses: missing/garbage/malformed, bad signature, expired, wrong purpose, wrong account, changed password (`pf`), advanced generation (`sg`), and any token not minted by this module (a session cookie, a step-up grant, a token signed with the raw session secret, the MFA key or the step-up key). The token grants nothing by itself; a second factor is still required (S7.5.3).

## 10. Implementation notes (added after build; the frozen behaviour above is unchanged)
- **Rotation guard:** `rotateMfaCredentialSecret` is guarded by the old **key id and nonce** (not the old ciphertext as §5 first described). The nonce identifies the exact ciphertext, is non-secret by design, and keeps ciphertext out of request URLs and access logs.
- **Enrollment support without enrollment:** `checkTotp` verifies a code against a *pending* credential without consuming a step (needed by the future confirmation step); `verifyAndConsumeTotp` accepts only *active* credentials and is the only login-grade verification. `newRecoveryBatch` returns plain codes and keyed hashes without persisting or logging anything.
- **Proof against the real stack:** `test-mfa-crypto-postgres-s752.js` stores application-encrypted secrets through PostgREST, shows the database holds ciphertext only, detects tampered and transplanted ciphertext, races 24 submissions of one code through two clients and two key rings (one winner), rotates concurrently, and checks every error for leaks with the database unreachable.
- **Retiring a key:** keep it in `LEAD_AGENTS_MFA_KEYS_PREVIOUS` until `rotateCredentialSecrets` reports nothing left to rotate **and** every account's recovery codes were regenerated (§5 rule, verified by test).
