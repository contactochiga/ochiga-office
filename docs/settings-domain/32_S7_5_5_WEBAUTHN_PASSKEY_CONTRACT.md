# S7.5.5 — WebAuthn / passkey integration: frozen contract

Branch `feature/settings-s1-s2`, starting HEAD `85966f8` (local = remote, clean worktree verified). Adds WebAuthn security keys and platform authenticators as a **second MFA factor type** inside the existing S7.5 architecture: the same account/session/generation binding, S7.5.1 tables and atomic functions, S7.5.2 challenge discipline, S7.5.3 login challenge and `/session/mfa/verify`, S7.5.4 step-up (`mfa_management`), credential management routes, recovery codes, notifications and audit. **No second authentication system.** Out of scope: passwordless/passkey-primary sign-in, attestation trust (metadata service), UI, MFA enforcement, the general step-up MFA leg (S7.5.6), reset flows (S7.5.7), merging, deploying, production migration or domain, S7.5.6.

## 1. Dependency (reviewed before use)
`@simplewebauthn/server` **14.0.3**, pinned exactly in `package.json`/`package-lock.json`. MIT; actively maintained (v14.0.3 published 2026-09, single maintainer `iamkale`, repository MasterKale/SimpleWebAuthn); Node ≥ 20 (project runs 25). **24 new packages**, all permissive (MIT ×21, BSD-3-Clause `asn1js`, Apache-2.0 `reflect-metadata`, 0BSD `tslib`): the `@peculiar/*` ASN.1/X.509 family, `@levischuck/tiny-cbor`, `@hexagon/base64`, `tsyringe`, `pvtsutils`, `pvutils`. `npm audit` on the new tree adds **zero** advisories; the tree's single high advisory is the **pre-existing direct dependency `axios`** (GHSA-vh66-26gq-q6x8 / prototype-pollution gadget, fix available) — unrelated to this slice and reported, not changed here. **All CBOR/COSE/attestation/assertion parsing and signature verification is done by this library; the repository contains no custom CBOR or COSE verification code.** (Tests use a software authenticator that *builds* messages with the library's own CBOR dependency, and one real-browser interoperability test with Chrome's virtual authenticator.) Deployment consequence: `npm install`/`npm ci` must run in the deploy build (it already does for `pg`, `axios`, `dotenv`).

## 2. Relying-party configuration (explicit; nothing invented)
`LEAD_AGENTS_WEBAUTHN_RP_ID` (registrable domain, lower-case, no scheme/port/path), `LEAD_AGENTS_WEBAUTHN_ORIGINS` (comma list of exact origins), `LEAD_AGENTS_WEBAUTHN_RP_NAME` (default `Ochiga Office`). Validation reports codes only: `webauthn_rp_id_missing|invalid`, `webauthn_origins_missing`, `webauthn_origin_invalid`, `webauthn_origin_rp_mismatch` (an origin's host must equal the RP ID or be a subdomain of it), `webauthn_insecure_origin` (`http` is allowed only for `localhost`/`127.0.0.1` and **never in production**), `webauthn_production_not_approved`.
**Production guard:** with `NODE_ENV=production` WebAuthn stays **unavailable** unless `LEAD_AGENTS_WEBAUTHN_RP_APPROVED` equals the configured RP ID exactly (the owner's explicit, deliberate confirmation that the permanent domain is approved; credentials are bound to the RP ID forever). No default, no domain is baked into the code, `render.yaml` or the documentation, and the deployment validator rejects an approval value or RP ID in `render.yaml`. Local development and tests use isolated `localhost` origins only. `/healthz` reports `mfa.webauthn.status` (`available`, `not_configured`, `invalid`, `awaiting_approval`) with problem codes; it never affects readiness (WebAuthn is optional while TOTP exists).

## 3. Challenge lifecycle
32 bytes of secure randomness per ceremony, stored through the S7.5.1 `admin_mfa_challenges` table (`webauthn_register` / `webauthn_authenticate`), lifetime 5 minutes (ceiling 15), bound to the account and purpose, **single use**: the challenge is consumed atomically *before* the response is verified, so a failed or replayed attempt cannot be retried against the same challenge (the client asks for fresh options). The challenge id travels with the response; the library compares the response's `clientDataJSON.challenge` with the stored value.

## 4. Registration
`POST /session/mfa/webauthn/register/options` → `register/verify`. Requires an authenticated **human** session (API keys/edge tokens refused), WebAuthn available, and the S7.5.4 `mfa_management` grant (password; plus a fresh second factor when the account already has one). Options: attestation `none`, user verification **required**, resident key `preferred`, algorithms restricted to ES256, EdDSA and RS256 (no post-quantum), `excludeCredentials` = the account's existing WebAuthn credentials, `userID` = an opaque per-account value (never the e-mail). Verification (library): challenge, origin(s), RP ID, user presence, **user verification**, attestation structure, public key. Then one atomic database step (the S7.5.4 activation function, extended): credential created, activated, first recovery-code batch if this is the account's first factor, session generation bumped; a database-enforced **limit of 10 active WebAuthn credentials per account**; the credential id is globally unique (duplicate registration, on this or another account, is refused with a generic conflict). The browser's session is re-issued with MFA proof; other sessions and grants end.

## 5. Authentication
- **Login:** the S7.5.3 challenge response lists `webauthn` in `methods` only when the account has an active WebAuthn credential **and** WebAuthn is available. `POST /session/mfa/webauthn/auth/options` (login challenge as proof, public path) returns options (`allowCredentials` = the account's active credentials, user verification required) and a challenge id. `POST /session/mfa/verify` accepts `method:"webauthn"` with `{challenge_id, response}`.
- **Step-up:** `POST /session/mfa/webauthn/step-up-options` (session) and `POST /session/step-up` with `mfa:{method:"webauthn", challenge_id, response}` give a fresh factor for `mfa_management`, exactly as a TOTP code does.
- **Checks, in order:** account-bound single-use challenge consumed; the credential named by the response must be one of **this account's active** WebAuthn credentials (ownership; revoked or foreign ids fail); library verification of origin (against the configured list), RP ID, user presence, **user verification (required)**, signature and counter; then the **counter compare-and-set** below. Any failure is the same generic `mfa_failed` (no oracle), counted by the persisted per-account failure counter and the login limiter, with an audit reason category. Configuration/library/database faults are 503 and never password-only.
- **Counter rule (atomic, new database function):** accepted only if `new > stored`, or both are `0` (synced passkeys report 0). A decrease or repeat is treated as a cloned or replayed authenticator: refused, audited as `webauthn_counter_rollback`. Replay protection for counter-0 authenticators comes from the single-use challenge, not the counter.

## 6. Credential lifecycle
Multiple WebAuthn credentials plus an optional TOTP per account. Listing (`GET /session/mfa`) returns only sanitised fields (id, type, label, status, created/last-used, transports, backup eligibility) — never credential ids, public keys or counters. Removal is the existing `credentials/:id/remove` route (step-up with a fresh factor, ownership enforced, last-active-factor guard counting **all** types, generation bump, notification). A revoked credential cannot authenticate. Recovery behaviour is unchanged: recovery codes sign an account in when authenticators are lost; with no authenticator and no code the owner route of S7.5.7 applies.

## 7. Schema (additive migration `20261025_admin_mfa_webauthn.sql`, service role only)
`office_mfa_webauthn_record_use(user, credential, new_count)` (atomic counter compare-and-set), `office_mfa_webauthn_version()` (PL/pgSQL probe — never a constant SQL function, see S7.5.4), and `office_mfa_activate_credential` re-created with the 10-credential limit. Non-destructive rollback restores the previous activation function and drops the new ones; credentials and counters are kept.

## 8. Audit and notifications
`mfa_webauthn_registration_started`, `mfa_enrolled` / `mfa_factor_added` (activation), `mfa_failed` (reasons: `challenge`, `unknown_credential`, `verification`, `counter_rollback`, `user_verification`), `mfa_verified` (method `webauthn`), plus the existing removal/notification events (`factor_added` notice added). Never: challenges, assertions, attestation objects, public keys, credential ids, secrets.

## 9. Required tests
