# S7 remediation R4 — current-session logout revocation: frozen contract

Starting HEAD `52fd137185d31b36a817aae1d507141f911d667d` (local = remote, clean verified). Closes certification finding F-5 / concern C1 (`26_S7_4_OUTSTANDING_PRODUCTION_CONCERNS.md`): after an ordinary logout a copy of the cookie stayed valid until expiry. Preserves S7.4 account-wide revocation (generation), S7.5.0 password fingerprint, S7.3 expiry, S7.5.3 MFA claims, S7.2/S7.5.6 step-up binding and the existing cookie attributes. No merge, deployment, production migration or MFA enforcement.

## 1. Audit of what exists
- **Token:** `base64url(JSON{email, role, user_id, permission_scopes, exp, sg, pf, mf?, mft?}).hex(HMAC-SHA256(secret))`. Nothing identifies *one* session; two sign-ins of the same account differ only in `exp`.
- **Issuance:** exactly one place, `issueSession` (login, MFA verify, invite accept, password change/reset re-issue, enrolment re-issue, sign-out-everywhere "keep current").
- **Verification:** one reader (`readAdminSession` via `authenticateSessionCookie`) plus one live-state check (`enrichAuthContext`: account loaded and active, generation, password fingerprint, MFA proof, enforcement). Every protected route and `/session/me` use it.
- **Logout:** `POST /session/logout` clears the browser cookie and writes an audit row; the signed token stays valid. Persistence available: account row (generation), versioned runtime settings, MFA tables, file store state in development.

## 2. Approaches compared
| Approach | Verdict |
|---|---|
| Bump `session_generation` on logout | rejected: signs the person out of **every** device (they expect only this one); the account-wide mechanism stays for "Sign out everywhere" |
| One "current session nonce" column on the account | rejected: supports a single session per account |
| Full server-side session table (valid sessions listed, looked up on every request) | rejected: converts the stateless design into a stateful one, a much larger change and risk |
| Bounded **in-process** denylist | rejected: lost on restart, not shared between instances |
| Existing runtime-settings table | rejected: versioned/audited configuration store with immutable history; wrong tool and unbounded growth |
| **Per-session identifier in the signed token + a durable revocation record keyed by a digest of it (a denylist whose entries live only as long as the token can)** | **chosen**: smallest change that gives durable, per-session, cross-instance revocation; unaffected sessions need no storage; entries are bounded by the session lifetime and pruned automatically |

## 3. Chosen design
- **Session identity:** a new claim `sid` = 16 cryptographically random bytes (base64url), generated at issuance and signed with the rest of the token. Added **only when the store reports the capability** (`supportsSessionIdRevocation`); otherwise tokens are issued exactly as today (deploy order does not matter). Tokens without `sid` (issued earlier, or on a database without the migration) are *legacy*: they keep working and can only be ended by the account-wide mechanisms, which is stated honestly at logout.
- **Never exposed:** `sid` is not returned by any API, never written to the audit log or application logs, never in browser storage (the cookie is HttpOnly and the page never reads it). The database stores only a **keyed digest** `HMAC-SHA256(key derived from the session secret for this purpose, sid)` (hex, 32 chars), so a reader of the table can neither forge nor correlate a session.
- **Storage (additive migration `db/20261026_admin_revoked_sessions.sql`, service role only):** table `admin_revoked_sessions(session_digest pk, admin_user_id → admin_users on delete cascade, revoked_at, expires_at)`; RLS on, no policies, nothing for `anon`/`authenticated`/PUBLIC; PL/pgSQL functions `office_revoke_session(digest, user, expires_at)` (idempotent insert, **self-pruning**: removes rows more than a day past their expiry), `office_is_session_revoked(digest)`, `office_session_revocation_version()` (probe). Guard: refuses to apply without the S7.4 migration. Rollback `db/rollback/20261026_admin_revoked_sessions.down.sql` drops the functions and **keeps the table** (dropping it would resurrect logged-out sessions). File store: a `revoked_sessions` map persisted with the rest of its state.
- **Verification:** `enrichAuthContext`, after the account/generation/fingerprint checks and before MFA policy, looks the digest up for tokens that carry `sid`. Revoked → `401 session_revoked` (reason `logged_out`). **The lookup failing → `503 session_verification_unavailable`: fail closed**, never "assume not revoked". Tokens without `sid` skip the lookup (no added cost for them).
- **Logout:** identifies the session from the *signature-verified, unexpired* cookie (no live account check, so a person can always log out). Responses: revoked → `200 {ok:true, revoked:true}`; no `sid` (legacy / capability absent) → `200 {ok:true, revoked:false, reason:"not_individually_revocable"}`; no valid cookie → `200 {ok:true, revoked:false, reason:"no_session"}`; the revocation cannot be persisted → `503 {ok:false, revoked:false, error:"logout_not_confirmed"}` with no database detail. **In every case the browser cookie is cleared.** Audit: `session_logout` with `revoked` true/false, or `session_logout_unconfirmed`; never the identifier.
- **Account-wide revocation unchanged:** generation bump, password fingerprint and removal/deactivation remain checked **before** the denylist, so they invalidate every session whatever its `sid`.
- **Step-up grants** are bound to the session (hash of the cookie); a revoked session's grants die with it. API keys and edge tokens have no session: logout with an API key alone revokes nothing and the endpoint accepts no identifier from the request body or query.
- **UI:** the existing sign-out button now reports an unconfirmed revocation (toast pointing to *Sign out everywhere*); nothing else changes.

## 4. Limits stated up front
Mixed versions: an instance older than R4 ignores `sid` and keeps accepting a logged-out copy (same class as F-6; fleet attestation is the control). Tokens issued before R4 or while the migration is absent cannot be revoked individually. One extra indexed lookup per authenticated request for tokens that carry `sid`. A request already authenticated before the revocation committed may complete (inherent to any revocation).

## 5. Required tests
Ordinary logout; copied cookie refused (single-use of the verb: second logout idempotent); two simultaneous sessions (other stays valid); account-wide and administrator revocation; password change; expiry; MFA sessions (claims preserved, copied MFA cookie refused); step-up grants die; database outage (verification 503, logout 503 + cookie cleared, no detail); restart persistence (file store and Postgres); concurrent logout and authentication; legacy tokens; API-key callers; redaction (no `sid` in responses, audit, logs; table holds only the digest). Disposable Postgres/PostgREST: migration order guard, idempotence, RLS and privileges, atomic/idempotent function under concurrency, pruning, rollback keeps data, two server instances, outage. Then R1–R3 tests, S7.0–S7.5.8, the frozen S7.5.9 certification suites, every Postgres suite and the complete regression with the R3 runner (true exit codes), and the gates.
