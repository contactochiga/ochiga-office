# S7.5.8 — Complete MFA user interface: frozen contract

Branch `feature/settings-s1-s2`, starting HEAD `c0666f7bd655737fb36dbf97a4ebb02c7c50565a` (local = remote, clean verified). The interface for the S7.5.0–S7.5.7 backend. **No new authentication system, no new auth route, no new secret, no migration.** MFA stays off by default: with `LEAD_AGENTS_MFA` unset no screen in this document appears, no request is added to ordinary pages except one `GET /session/mfa` when the step-up dialog opens or the security panel is opened.

## 1. Audit of what exists (before this slice)
- **One module, `public/office/office.js`** (ES module, `/office.js`), vanilla DOM helpers `el`, `escapeHtml`, `api` (fetch wrapper that throws `{status,data}`), `toast`, Settings components `stCard`, `stSafe`, `stErrorWithRetry`, `stConfirmDialog` (focus-trapped modal), `stRegistryEditor` (governed settings editor), `stRenderPeople` (People & Access), and the S7.2 `OfficeStepUp` password dialog (`window.OfficeStepUp`, grants held in memory only).
- **Login** (`#loginForm`, `wireLogin`): `login()` assumed `data.admin`; a `mfa_required` response (HTTP 200, no cookie) would have left the page signed out with no way forward. There is no global 401 handler: a session ended server-side by revocation, MFA or enrolment rules only surfaced as failing requests.
- **Step-up dialog** asks for the password only; an enrolled account's grant also needs a fresh second factor (S7.5.6), so every step-up consumer (registry editor, revocation, MFA management) would fail.
- **People & Access** ended with an "Unavailable: MFA…" placeholder; Settings is reachable only with `settings.manage`, but MFA self-management (`mfa_management`) is open to any signed-in person.
- **Static assets** are served from explicit routes in `server.js` (no directory serving).
- **QR:** no browser QR generator exists; `src/lead-agents/qr.js` is a server-side placeholder pattern, not a scannable code.

## 3. Screens
**3.1 Login challenge** (inside the existing login card; password-first flow unchanged). Shown when `/session/login` answers `mfa_required`. Methods offered are exactly `methods` from the server: *Authenticator app* (6-digit code), *Security key or passkey* (only if the server lists `webauthn` **and** the browser supports it), *Recovery code*. Errors by server code: `mfa_failed` (wrong code), `mfa_challenge_expired` (sign in again), `mfa_locked` (+ minutes from `retry_after_seconds`), `login_rate_limit_exceeded`, `mfa_unavailable`/`mfa_verification_unavailable` ("not signed in", never a password-only path). The session exists only after the server answers `200` with `admin` and sets its cookie; the UI never marks the user signed in on its own. A recovery-code sign-in shows the remaining count and offers to regenerate. The challenge token lives in a closure variable only.
**3.2 Forced enrolment** (answer `mfa_enrollment_required`; no session, TOTP only): explain → *Send a code to my email* (always the same neutral message) → enter the mailbox code → authenticator setup (3.4) → recovery codes (3.5) → back to sign-in. A WebAuthn forced-enrolment ceremony does not exist in the backend contract; a security key can be added after the first sign-in.
**3.3 Grace notice:** the server's `mfa_enrollment` object (login response / `/session/me` `mfa.enrollment`) renders a banner in the shell: days left, end date, *Set up now*. Dismiss lasts the page view only.
**3.4 Authenticator setup:** locally generated QR (SVG), grouped manual key with Copy, 6-digit confirmation. Enrolment secrets are never sent anywhere except our own begin/confirm endpoints; no image or service URL is ever built from them.
**3.5 Recovery codes:** shown once, from the server response, in memory. Copy, Download (`.txt` Blob), Print (isolated frame), a required acknowledgement before *Done*. Never in `localStorage`/`sessionStorage`/IndexedDB/cookies/URL; cleared from the DOM and variables on completion.
**3.6 Two-step verification card** (Settings → People & Access, and a footer button for everyone, opening the same panel in a dialog): mode (off/not enabled shown truthfully), enrolled factors with type, label, added and last-used times, remaining recovery codes, *Add authenticator* / *Replace authenticator*, *Add security key*, *Remove*, *Regenerate recovery codes*. Every change goes through the step-up dialog (3.7) with purpose `mfa_management`; results shown are the server's confirmations.
**3.7 Step-up dialog (extended, same `OfficeStepUp` handle):** password plus, when the account is enrolled (known from `GET /session/mfa`; if that cannot be read, an optional factor field is offered), *Authenticator code* or *Security key*. The `mfa` object is sent as the backend defines; recovery codes are not offered. All existing consumers inherit it.
**3.8 Administrator reset card** (visible to `super_admin` with `team.manage`): choose a person, reason (3–500 characters), retype their email, explicit confirmation, `mfa_management` step-up with a fresh factor; shows only the server's confirmation (credentials revoked, sessions ended, notification status, re-enrolment required).
**3.9 Enforcement card** (`staff.manage` to view; write controls need `team.manage` and `super_admin`): current level and version from the registry setting; level selector; **preflight** for the chosen level (each check with plain wording, affected-account counts, recovery readiness, fleet readiness, grace deadlines per unenrolled account); *Apply* is available only after the preflight for that level returned `ok`, then uses the registry endpoint with `expected_version`, `confirm: true` and a `security_policy_write` step-up. The server re-runs preflight; a `412`, `409` or `403` is displayed as such.

## 4. Backend additions (read-only)
`GET /session/mfa/enforcement/preflight` additionally returns `current: {level, status, effective_since}`, `grace: {days: 14}` and `accounts: [{id, email, display_name, role, deadline, expired, source}]` (unenrolled accounts the checked level would cover, at most 200, `staff.manage` only; for the level in force the deadline is the real one). Two new `GET` routes serve the module files. Nothing else changes.

## 5. Security rules (tested)
No MFA secret, TOTP secret, recovery code, challenge token, enrolment token or step-up grant in `localStorage`, `sessionStorage`, IndexedDB, cookies, URL, console or audit. No third-party request at all (QR is local; verified by recording network requests during every flow). No client-side authorization: buttons reflect `GET` results but every action is re-authorized by the server and a server refusal is shown as a refusal. No optimistic success: state changes only after a `2xx`. No password-only fallback for enrolled accounts: a failed or unavailable factor never creates a session. A response that ends the session (`401` with `session_revoked`, `mfa_required`, `mfa_enrollment_required`) returns the user to sign-in with the reason. All dynamic text is set with `textContent` or escaped; the QR SVG is built from booleans.

## 6. Accessibility and responsive
Design-system tokens only. Dialogs: `role="dialog"`, `aria-modal`, labelled title, focus moved in, trapped, restored; Esc cancels everything except the recovery-code dialog (acknowledgement required). Method switch is a labelled button group with `aria-pressed`; errors in `role="alert"`, progress in `aria-live="polite"`; inputs have visible labels, `autocomplete="one-time-code"`, `inputmode="numeric"`; touch targets ≥ 44 px at ≤ 768 px; no horizontal overflow at 1440, 1100, 900, 768, 390 px; QR has a text alternative; status is never colour-only. Screenshots at those five widths are committed under `docs/settings-domain/s7-5-8-evidence/`.

## 8. Known limits (declared up front)
Forced enrolment is TOTP only (backend contract). No UI to list per-device sessions (no contract). Passkey-only sign-in does not exist (a password is always first). The QR library is third-party code (vendored, pinned, reviewed above).
