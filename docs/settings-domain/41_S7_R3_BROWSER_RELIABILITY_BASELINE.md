# S7 remediation R3 — browser test reliability: root-cause audit and frozen baseline

Starting HEAD `b8f4ca82fc839b2bf060ece2fe8eb8a80b3db820` (local = remote, clean verified). Scope: **test infrastructure only**. No application behaviour is changed to satisfy a browser test; no assertion is removed or weakened; no S1–S7 contract is touched.

## 1. Affected suites and current settings
Sixteen scripts drive headless Chrome through hand-copied CDP code (15 suites plus `capture-settings-visual-acceptance.js`): `test-settings-{domain,registry,providers,organization,locale,operations}-browser`, `test-s5-integration-acceptance`, `test-auth-step-up-browser-s72`, `test-session-policy-browser-s73`, `test-session-revocation-browser-s74`, `test-mfa-webauthn-browser-s755`, `test-mfa-ui-browser-s758`, `test-relationship-workspace-browser`, `scripts/cert/cert-browser.js`. Common settings today: CDP call timeout 20 s (settings suites, S5) or 30 s (S7.x, S7.5.x, cert); fixed debugging ports 9347 and 9351–9363 (**9353 is used by two scripts**); Chrome launched with `--headless=new --disable-gpu --disable-features=BackForwardCache` and a temp profile; cleanup = `chrome.kill()` (SIGTERM to the main process only, not awaited, helper processes not targeted), profile removal only in some suites; no suite waits for a navigation to settle; a few have a "retry once on timeout" wrapper around `Page.navigate`. There is no in-repo runner: `npm test` is `npm run check`; the complete run is an external loop (900 s per suite).

## 3. Root cause (instrumented, not assumed)
A diagnostic copy of the failing suite dumped, at the moment of the stall: Office server connections = **0**, `/healthz` answered in 6 ms (server healthy), Chrome reported **two EventSource requests still in flight** (age 20–24 s) and the page lifecycle log showed: `frameStartedNavigating about:blank` → `frameStartedNavigating …/office#/settings` → **then** `frameNavigated about:blank`. So:
1. `useCookie` sends `Page.navigate about:blank` and returns as soon as Chrome *accepts* it (the CDP reply precedes the commit); the suite does not wait for the commit.
2. The suite immediately sends `Page.navigate …/office#/settings`. The still-committed document is `…/office#/settings/communications`, which differs from the target **only by its fragment**, so Chrome classes the request as a same-document navigation.
3. The pending `about:blank` navigation then commits, replacing the document; the same-document navigation is dropped and its CDP call never answers.
Long-lived EventSource requests of the unloading Office page (the shell opens `/admin/events`) delay that commit and widen the window, which is why it is intermittent (about 1 in 6) rather than constant. It is a **test race**, not a server, port, memory or CPU problem (idle host; server healthy; 66/66 for the others). Every suite shares the same unguarded `about:blank` → URL pattern (latent exposure), but only the suite whose previous page ends on a fragment-only neighbour of the next target trips it. Secondary defects found: fixed ports with a duplicate (9353) make parallel runs drive each other's browser; `SIGTERM` to the main Chrome process without waiting leaves helper processes and profile directories behind and makes the next suite start while the previous browser is still shutting down (visible CPU/memory contention in long runs).

## 4. Expected corrections (what R3 will do, nothing else)
1. `scripts/lib/browser-harness.js`: `launchChrome` (own process group, `--remote-debugging-port=0` and the real port read from `DevToolsActivePort`, awaited graceful stop with escalation, profile removal) and `wrapSend` (`Page.navigate`/`Page.reload` settle before returning; marker-based commit detection; fragment-only navigations handled explicitly; **one** bounded recovery that is always counted and printed; `BROWSER_HARNESS_STRICT=1` makes any recovery a failure).
2. Mechanical adoption in every browser suite: port, spawn, `send`, cleanup lines only. **Test bodies, assertions and fixtures are untouched** (verified by a diff review limited to those lines).
3. `scripts/run-all-tests.js`: an in-repo sequential runner with explicit per-suite timeout budgets (default 120 s, browser suites 300 s, the MFA UI and certification browser suites 900 s), scoped cleanup of leftover browsers it started, and a summary that never reports a suite as passing from an isolated rerun.
4. Validation recorded: strict-mode repeated runs on an idle host, under the complete-suite load, in parallel (now possible), and under constrained CPU and memory. Any remaining failure is classified and kept.
