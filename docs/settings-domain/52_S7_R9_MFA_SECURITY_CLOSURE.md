# S7 R9 — MFA Security Closure

Baseline R8 `e534a94`. Runtime/schema commits `3ee2f2b`, `a06d078` (final). Clean-checkout evidence: `s7-official-results/r9` (gates, full, Postgres, cert, frozen A–D on `a06d078`). Nothing was merged, deployed, migrated in production, or MFA-enforced.

## Root causes
1. **Empty/untrusted factor list.** "Does this account have an active factor?" (`hasActiveMfa`) was answered by ONE read of `admin_mfa_credentials`. An empty, truncated or stale answer made an enrolled account read as unenrolled, so the password alone signed in (frozen c05 `DEP-MFA-emptylist`, reproduced against the pre-R9 schema by `R9-101`). A malformed shape (`{}`) was already refused (R8); a well-formed empty list was indistinguishable from "verified zero".
2. **Mailbox-code guessing.** The 8-digit forced-enrolment code derives from a signed, stateless challenge (`jti`). Only a rate limiter bounded guessing (per-process or address-keyed), so spoofed addresses, restarts and bursts weakened the bound (frozen b5 `F7.30`).

## Schema changes (additive; no row, hash, account, session or credential is modified)
**`db/20261030_mfa_active_factor_evidence.sql`** (needs `20261022` foundation; refuses otherwise): `admin_users.mfa_active_count integer not null default 0 check (>= 0)`; functions `office_mfa_sync_active_count(uuid)`, `office_mfa_active_count_trigger()`, `office_mfa_evidence_version()`; trigger `admin_mfa_credentials_active_count` (after insert / update of status, admin_user_id / delete) keeps the count equal to the number of `active` credentials in the same transaction; one-time backfill of accounts already enrolled; all functions service_role-only. Quiet when nothing changes (no lock, no `updated_at` bump); counter updates (TOTP step, WebAuthn sign count) do not fire it.
**`db/20261031_mfa_mailbox_attempts.sql`** (needs `20261022`): table `admin_mfa_mailbox_attempts(admin_user_id → admin_users on delete cascade, challenge_id, attempts, expires_at, pk(admin_user_id, challenge_id))`, RLS on, no policies, service_role only; functions `office_mfa_mailbox_version()` and `office_mfa_mailbox_attempt(user, challenge, expires, max)` (one atomic upsert per evaluation; expiry capped at 15 min; 2 % opportunistic pruning).
Rollbacks `db/rollback/20261030…down.sql` (drops trigger/functions; **keeps the column and all credentials**; the application falls back to the pre-R9 single read) and `…20261031…down.sql` (drops the ephemeral counters; falls back to the account lock and limiter). Both repeatable and re-appliable (tested).

## Store and server contract
- **`hasActiveMfa(userId)`** decides from two independent reads: the active credential ids and the account's own `mfa_active_count`. They must be integers/arrays and EQUAL; otherwise `mfa_store_error` (callers answer 503, never "no factor"). **Verified zero** (marker 0 and no rows) is the only unenrolled result. Empty, truncated, stale, wrongly-typed, missing-row, HTML/garbage/5xx answers and database drift all fail closed. File store: refuses a corrupt population (non-list, null entries) the same way.
- **Capability/readiness:** `supportsMfaEvidence()` (probe `office_mfa_evidence_version`). Without the migration the store keeps the pre-R9 behaviour and `/healthz` shows `mfa.evidence: "unavailable"`; **with MFA mode ON that makes `/healthz` not ready (503)** so a fleet cannot run MFA without the evidence. `mfa.mailbox_attempts` is reported (informational).
- **Mailbox verify** (`POST …/mfa/enroll/email-verify`): (1) account-level progressive MFA lock checked first; (2) `recordMailboxAttempt` — 5 evaluations per (account, challenge), persisted and shared (Postgres) or persisted in the state file (file store, survives restart); (3) wrong code also records the account failure (5/10/20 ⇒ 1/15/60 min locks, shared with TOTP/recovery guessing); a correct code does not clear failures. Spoofed forwarding headers, restarts, other instances and concurrent bursts cannot reset or bypass it. A store fault answers 503 and the code is NOT evaluated. A correct code may be re-verified within the challenge lifetime (the frozen S7.5.8/S7.5.9 contract: the enrolment token is what is single-use) but each evaluation spends the same budget. Without the migration the account lock and limiter remain.
- Unchanged: TOTP, WebAuthn, recovery codes, factor management, step-up, session generation and enforcement code paths.

## Migration order, staging and production dependencies
Order: base schema → … → `20261026` → R5 `20261027` → R6 `20261028`, `20261029` → **R9 `20261030`, `20261031`**; rollback newest-first. Only `20261030` is tied to MFA readiness; `20261031` degrades gracefully.
Staging verification: apply both; `GET /healthz` ⇒ `mfa.evidence: "available"`, `mfa.mailbox_attempts: "available"`; run the three audit queries below (all expected to match); enrol a test account and confirm sign-in still requires the factor; run `scripts/test-mfa-closure-postgres-r9.js` against a disposable copy (never production). SQL: `select count(*) from admin_users u where mfa_active_count <> (select count(*) from admin_mfa_credentials c where c.admin_user_id = u.id and c.status = 'active')` ⇒ 0.
Deployment order for a fleet: **apply `20261030` BEFORE (or with) the R9 code when MFA mode is ON** — new code without it reports not-ready (503) by design. Mixed versions are safe: old code ignores the column and the trigger keeps it true; new code on an un-migrated database falls back and reports it.
Rollback safety: no credential or account is touched by apply or rollback; after the evidence rollback the column is stale but unused.
Still required by earlier slices and still open: R5 production database audit and migration `20261027`; R6 `LEAD_AGENTS_TRUSTED_PROXY_HOPS` and `20261028`/`20261029`.
