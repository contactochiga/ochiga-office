## Backend forwarding (`whatsapp_webhook.backend_forward_failed`, 8,000 ms timeout)
Mechanism: Office forwards every inbound message and every status callback synchronously to Backend `POST /office/communications/webhook-event` with an 8 s axios timeout; on failure Office logs and continues (CRM intake is unaffected).
Evidence from the Backend's own database (project `zcpgtdakqxyvjkmiibei`, read-only aggregate queries, no message content):
1. **Status callbacks are received and persisted**: `oyi_communication_events` holds communication.sent 47 / delivered 56 / read 54 (and 6 failed) from 2026-08-22 through 2026-10-15.
2. **Inbound messages are NOT persisted**: `oyi_communications` has only 7 inbound WhatsApp rows (all 2026-08-22) and 20 WhatsApp rows in total, none after 2026-08-26, while Office stored 56+ inbound messages; the two genuine messages received today after the deploy produced no Backend row and no Backend event.
3. **Root cause of that, reproduced**: the Backend inbound pipeline (`inboundEventPipeline.ts`) persists with `upsert(..., { onConflict: "provider,provider_message_id,direction", ignoreDuplicates: true })`, but the only matching unique index (`uq_oyi_communications_inbound_provider_message`, migration `20260823100000`) is a **partial** index (`WHERE provider_message_id IS NOT NULL AND direction = 'inbound'`). PostgreSQL cannot infer a partial index from a bare column list. A planner-only `EXPLAIN` of the same statement against the production Backend database returns `42P10: there is no unique or exclusion constraint matching the ON CONFLICT specification` (nothing executed, nothing written; verified 0 probe rows). Every inbound message that reaches the pipeline therefore fails at the first insert and the route answers `ok:false` (`inbound_event_persist_failed`).
4. The 8,000 ms **timeouts are a separate, intermittent symptom**: they are not explained by the 42P10 failure (that returns immediately). Backend logs and Render plan details are not accessible, so the cause is not proven; the likely candidate is Backend instance wake-up/latency (the status forwards succeed the rest of the time). Whether a timed-out request still reached Backend cannot be proven without Backend logs; for inbound messages the outcome is the same either way (no persistence).
Impact: Backend/Oyi Core never sees inbound customer messages (no goal wake, no classification, no opt-out/STOP governance on inbound text, no canonical thread for replies) while Office CRM intake works. With autonomy OFF nothing is sent, so there is no customer-facing misbehaviour, but Backend's inbound intelligence path has been dead since 2026-08-23.
Not changed: no Backend or communication-architecture change was made (Backend deployment/migration not authorised). Minimal fix options for a separate, approved Backend change: (a) replace the upsert with a plain insert and treat unique-violation 23505 as the duplicate case, or (b) add a full (non-partial) unique constraint on (provider, provider_message_id, direction) and keep the upsert (note: outbound rows with NULL ids are unaffected by a unique constraint because NULLs are distinct). Either needs a Backend release and, for (b), a migration plus a replay decision for the ~49 missed messages (idempotent re-forward from Office's stored inbound events is possible because the Backend dedupes on provider message id).
