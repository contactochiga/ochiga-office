## Design (Office-owned queue of communication EVIDENCE)
* **Table** `communication_delivery_outbox` (additive migration; RLS on, no anon/authenticated access): `delivery_key` UNIQUE (`whatsapp:message:<provider id>` / `whatsapp:status:<provider id>:<status>`), event type, provider id, lead, exact Backend request `payload` (original provider id, sender, text and PROVIDER timestamp), `mode` (live|replay), `status` (pending|delivered|dead), `attempts`, `next_attempt_at`, `lease_until`/`leased_by`, `last_error`, `last_http_status`, `last_attempt_at`, `delivered_at`, `dead_at`.
* **Enqueue**: right after the inbound event is stored (messages and status callbacks). PostgREST cannot span tables in one transaction, so the entry is written immediately after the event and a failure is logged and recoverable: the event stays in `inbound_events` and **reconciliation** enqueues any event that has no entry. A duplicate Meta delivery maps to the same key (no second pending entry).
* **First attempt inline and LIVE** (8 s, unchanged behaviour): Backend may wake a goal and returns `goal_active`, so the existing single-responder rule is preserved exactly. **Every later attempt — and every reconciled/historical entry — is sent with `replay:true`** (Backend persists + classifies + honours STOP, never wakes a goal, never sends) and its `goal_active` answer is ignored. The queue therefore cannot become an autonomous reply scheduler.
* **Outcome rules**: delivered only after HTTP 200 with `ok:true` (a Backend duplicate acknowledgement also counts). Timeout / dropped connection = *ambiguous*, treated as possibly delivered: stays pending and is retried (Backend is idempotent on the provider id). 5xx, 408, 429, 401, 403 and `ok:false` processing failures are retried; 200 `ok:false` with `unsupported_or_missing_fields|missing_sender|unrecognized_status` and other 4xx are permanent → dead letter immediately.
* **Retry configuration** (defaults in `communication-outbox.js`, overridable via `config.communicationOutbox`): background attempts use a 45 s timeout (rides out a cold start); backoff `30 s × 2^(attempt−1)`, capped at 30 min, ±20 % jitter; 12 attempts (≈ 5–6 h) then `dead`; lease 90 s; worker tick 15 s, batch 5. Worker runs automatically in production (`environment=production`), picks up leftovers 2 s after start, and stops with the server.
* **Concurrency**: a lease is a compare-and-set on `(status=pending, attempts)` (a single PostgREST PATCH in Supabase): of N concurrent workers/instances exactly one forwards an entry; a crashed worker's lease simply expires and another worker completes it. Outcomes that could not be recorded after the POST leave the lease to expire and the entry is retried (never lost; Backend dedupes).
* **Admin endpoints** (`manage_integrations`, audited): `GET /api/lead-agents/admin/communications/outbox` (counts, due/in-flight, oldest pending, recent undelivered entries with shortened ids and no message text); `POST …/outbox/reconcile` (`dry_run` defaults to TRUE, window in minutes; creates replay entries); `POST …/outbox/recover {provider_message_id}` (single-event recovery: re-queue + attempt one stored message as a replay); `POST …/outbox/retry {id}` (re-queue a dead letter as a replay).

## Tests (`npm run office:communication-outbox:test`)
Real Office server + Backend stub that models Backend idempotency and a spy on every customer-facing send. (1) Backend available: delivered inline, live semantics, valid ack recorded, `goal_active` honoured; (2/3) Backend asleep / request timeout: message, CRM activity and event retained, retry with replay semantics delivers once with the original timestamp; (4) Backend commits but the response is lost (late response and dropped socket): not marked delivered until acknowledged, retry is an idempotent duplicate; (5) duplicate Meta deliveries (messages and statuses): one entry, one Backend event; (6) 6 workers racing for one entry ⇒ one forward; 3 sweepers over 5 entries ⇒ each exactly once; (7) 401/403: retried, dead-lettered after the bounded attempts, admin re-queue, delivered once; (8) 429/500/503: exponential backoff 40/80/160 ms with a cap, jitter within ±20 %, permanent refusal dead-lettered immediately, processing failure retried; (9) worker crash: lease blocks others then expires, restarted worker delivers as replay, background worker drains leftovers; (10–13) historical reconcile with autonomy OFF: dry run default, admin only, entries are replay, original Meta timestamps/sender/lead/provider id preserved, reconcile idempotent, no duplicate Backend events, **0 customer-facing messages in the whole suite**, autonomy setting never written; single-event recovery of the incident shape (original id/timestamp/sender/lead, exactly one Backend record, Office's event byte-for-byte unchanged, second call = already delivered, unknown id = 404); enqueue failure never blocks intake and reconciliation recovers it; no queue entries without a configured bridge. Store-level contract test (`test-communication-outbox-store.js`, store API only — also run against the real Supabase store with two client connections): unique identity under concurrent enqueue, lease with exactly one winner among 8 concurrent workers, expiry after a crash, due/backoff scheduling, transitions, summary, event listing.

## Limits / risks
* On the Render **Free** plan Office itself sleeps when idle; the background worker only runs while Office is awake. Entries wait durably in the database and are drained after the next wake (any webhook, or a request). A paid always-on instance would remove this gap (not changed).
* Backend remains the system of record for communication threads; if Backend is down for longer than the retry budget (~5–6 h) entries are dead-lettered (visible in diagnostics) and can be re-queued.
* The enqueue is not in the same database transaction as the inbound event (PostgREST limitation); the reconciliation scan is the safety net.
