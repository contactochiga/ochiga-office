Date 2026-10-14. Nothing was deployed, merged into a production-tracked branch, migrated in production, or enabled. No production data was modified or deleted; no environment variable or Meta credential was touched; no message was sent to any real number.

## 1. Executive summary
The autonomy switch was re-based onto what production actually runs, by cherry-picking only the autonomy commits onto the current production tips (no merges, no force). The two blockers are resolved as follows. **Branch divergence:** both release candidates apply cleanly (zero textual conflicts) on `codex/office-extraction` and `main`, and all Office (28 wired + 13 unwired) and Backend checks pass on them; one unrelated Wave 10 commit that is *not* in production (`b071f23`) was deliberately excluded. **Duplicates:** read-only forensics of production show the historical duplicates are genuine Meta webhook retries that *did* cause duplicate AI replies and, in two cases, duplicate leads; a guarded unique index would have been silently skipped. It is replaced by an additive **claim-first** mechanism (`whatsapp_inbound_claims`, primary key = Meta message id, seeded from history, nothing deleted) that is verified under true concurrency on a throw-away Postgres 16. A safe rollback build that keeps autonomous replies off was also prepared.

## 8. Selected non-destructive idempotency solution
Option B (separate canonical claim table) with a read-only backfill from history. `whatsapp_inbound_claims(provider_message_id PRIMARY KEY, status processing|completed, lead_id, claimed_at, completed_at, reply_sent_at, request_id)`, RLS on (service credentials only). The webhook handler **claims the Meta message id first** (`INSERT … ON CONFLICT DO NOTHING`, i.e. PostgREST `resolution=ignore-duplicates`) before any lead is created or reply drafted: the loser acknowledges and stops, so retries neither re-answer nor create a second lead. A stale `processing` claim (> 5 min) can be taken over by exactly one retry via one conditional `UPDATE`; a completed claim is never taken over; a takeover that finds `reply_sent_at` set never replies again. The claim is seeded from history (one `completed`, already-answered claim per distinct historical message id), so a late Meta retry of an old message — including the 5-copy one — cannot trigger a reply. No history row is touched. The guarded unique index from the earlier design is removed: it would have been skipped in production because of the 8 groups.
Failure modes: claim table/transport error ⇒ message still stored in the CRM, **no autonomous reply** (`claim_unavailable`); event without a provider id ⇒ stored, no autonomous reply; crash after claiming ⇒ a retry after 5 min completes ingestion exactly once and never re-sends a reply that was recorded as sent; crash between sending and recording the send ⇒ one possible repeat reply after the stale window (documented residual). Different message ids from one brand-new phone arriving concurrently can still create two leads (pre-existing, outside this change).

## 15. Deployment dependencies and safe rollback
Order: migrations → Backend → Office (Render auto-deploys the production branch on merge, so merging is the deployment: do not merge until approved; consider pausing auto-deploy for the window). Backend before Office, otherwise staff-confirmed Oma WhatsApp sends are blocked while OFF.
**Rollback that preserves OFF:** (1) first line of defence is the switch itself (Settings → OFF, instant, no deploy). (2) Do **not** redeploy the previous Office commit: it replies automatically. (3) If Office code must be rolled back, redeploy `release/whatsapp-autonomy-office-rollback-safe` (`a0bd54e…`), production plus one static rule: no autonomous WhatsApp send of any kind, inbound still stored and forwarded; it also blocks staff-confirmed Oma sends because it cannot verify attestations. (4) Backend rollback is safe either way (an old Backend's unlabeled sends are treated as autonomous by the new Office and blocked while OFF). (5) Migrations may remain (additive); drop scripts are in `db/rollback`. Without step 3, rollback would be a release blocker; with it, it is not.
